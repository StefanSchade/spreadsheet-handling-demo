= Demo Feature Matrix

This document captures the capabilities we want the demo repository to make visible.
It is not yet a user guide. It is the planning layer between the core library and a
future walkthrough-oriented demo dataset.

== Why This Lives In The Demo Repo

The demo repository is our current consumer benchmark. That makes it the right home
for:

* the feature inventory we want to demonstrate
* the reference datasets we will curate
* the walkthrough docs that explain how JSON, pipeline config, and spreadsheet output
  relate to each other

The main repository remains the source of implementation details, FTR history, and
internal architecture notes.

== Scope

The goal is not to show every internal subsystem. The goal is to show the user-facing
capabilities that matter when building or reviewing spreadsheet workflows.

== Roundtrip Stance

Our primary demo shape is:

. JSON as the source of truth
. pipeline config as the transformation contract
. Excel as the editable working format
. JSON re-export as the closing roundtrip step

This should work for most of the user-facing flows we want to demonstrate. Some
capabilities may currently be stronger on the Excel-to-JSON side than on the reverse
direction. We should track those explicitly instead of hiding them.

== First Demo Slice: Products

The first curated demo should use a business-friendly product theme. It is easy to
understand, broadly reusable, and expandable without domain-specific knowledge.

The first slice should stay intentionally small:

. `product`
. `product_manager`
. `branch`

Initial relationship shape:

* product n:1 product_manager
* product_manager n:1 branch

This gives us a useful first benchmark:

* multiple related sheets
* visible FK helper columns
* validation of references
* spreadsheet-friendly output
* later room for plugin-driven summaries

=== Proposed First Data Shape

For the first slice we favor simplicity over perfect business naming inside the core FK
mechanism. That means the initial JSON tables use the common columns `id` and `name`,
because the current helper pipeline works most cleanly when all target sheets share the
same identity and label fields.

Example:

* `product.id`, `product.name`, `product.id_(product_manager)`, `product.status`
* `product_manager.id`, `product_manager.name`, `product_manager.id_(branch)`, `product_manager.email`
* `branch.id`, `branch.name`, `branch.country`, `branch.region`

This still reads as a business model, while fitting today's FK helper behavior without
extra plumbing.

=== What This Slice Should Demonstrate First

. FK-derived helper columns next to reference fields
. workbook-level UX such as auto-filter, freeze header, and header styling
. sheet-specific overrides for visible per-sheet differences
. dropdown-style list validations for selected business fields
. referential validation
. clean JSON -> XLSX -> JSON storytelling

The join-like summary table should come later, once the base three-sheet story is
stable and easy to explain.

=== Current Product Slice Result

The first product slice now runs through both directions:

* JSON -> XLSX via `demo_product_business_slice.yaml`
* XLSX -> JSON via unpack into a temporary output directory

For this slice we currently flatten headers before writing so that helper columns come
back as readable JSON keys such as `_product_manager_name` instead of tuple-like
serialized header values.

It also demonstrates two more spreadsheet-facing features:

* list validations for `product.status`, `product.category`, and `branch.country`
* per-sheet overrides from `overrides.yaml`, with visible differences in filter,
  freeze, and header styling between sheets
